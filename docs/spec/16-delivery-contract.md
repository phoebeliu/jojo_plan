# 交付约定、依据与变更闭环

S1｜2026-10-02｜JP-1.1 补充设计。约束 FR-07/11/12/15/17/20/21 的具体体验与内容，不新增全局导航或命令。以下为待实现规范，静态演示不提供运行服务。

## 1. 用户可理解的交付约定

主协调者根据输入提出「交什么、怎样检查、哪些条件不包括」；用户可先推演，关键未知保持显式。不是强制填写长表，也不把一句聊天同意当作版本审批。

交付约定不是新数据库实体：使用现有 prd（系统）、skill/skill_group（技能）或 document（文档）产物的 metadata.deliveryContract，随 artifact_version 一起封版。Schema版本值为 `delivery-contract/1`。正文展示同样内容，结构化索引为检查依据；两者不一致拒绝封版。PPT后续也复用该结构。

| 字段 | 类型与约束 | 作用 |
| --- | --- | --- |
| schemaVersion | 固定字符串 delivery-contract/1 | 内容契约版本；未知版本不参与验收 |
| criteria | 非空数组，最多200项 | 小任务建议1–3项；系统按需求逐步细化 |
| criteria[].id | 本约定内唯一非空字符串 | artifact_link.requirement_key使用此值 |
| statement | 非空字符串 | 清楚可检查的预期结果，不用“品质很好” |
| method | runner / human / both | 自动检查、人工判断或两者 |
| expected | 非空字符串 | 检查对象、阈值/预期及范围 |
| required | boolean | 是否交付阻断条件；降级须走变更 |
| evidenceVersionIds | 去重字符串数组，可空 | 必须存在、同项目且权限允许的不可变版本；空为缺证据 |
| exclusions | 字符串数组 | 不在承诺范围内的情形 |
| assumptions | 字符串数组 | 未获确认的前提，不算事实 |

涉及审批的人与时间不写成可被Agent伪造的metadata状态，仍来自 approval 与绑定指纹。此补充细化原metadata JSON内容约束，不变更既有RPC envelope、SQL表或52方法数量；应用层负责结构与引用检查。当前 validate_spec.py 不检查这些新增内容约束，实施须按下述DC用例补检查，不能只因通用JSON合法就接受。

## 2. 关系与可信度

consumer→producer复用 artifact_link：设计 implements 需求；测试结果 verifies 受测成果；结果 references 来源；关键输入 depends_on。每条关联写 criterion id 为 requirement_key；适用范围由被引用的约定版本确定，禁止跨版本仅按ID复用结果。源文件定位复用source_span，不复制一段没有出处的模型文字冒充证据。

详情按「要求→当前目标版本→检查方法→依据版本/定位→结果来源→仍缺什么」展示。runner结果必须对应工具操作和真实受测版本；Agent自述通过仅为待核实材料。人工判断绑定相同baseline fingerprint。导入外部日志先为未核实材料，不能伪装本机runner记录。

图的缺边、解析失败、未建索引显式显示「覆盖尚未核对」。规则只能保守处理已知依赖，不能把未发现影响说成无影响。真正的业务准确性需要领域评审和样本；结构验证并不代替它们。

## 3. 状态是推导结果

| 展示状态 | 条件 |
| --- | --- |
| 待约定 | criteria为空、结构不合格或关键范围缺失 |
| 缺依据 | 必需依据缺失、引用失效或权限不允许读取 |
| 待检查 | 有成果但缺该版本的可信检查/人工审阅 |
| 未通过 | 任一当前必需检查失败 |
| 需重验 | 上游版本改变、所依赖baseline invalid或指纹不匹配 |
| 当前依据满足 | 对当前版本的必要检查和审阅均满足；不等于整个项目已交付 |

界面逐项显示原因；混合状态汇总为阻断项清单，不用平均分或“智能完成度”。工程/综合审核与生产授权仍按原流程；一项规则通过不能越过整个系统验收。手动接受例外只在现有政策允许范围内进行，留理由和指纹，不允许豁免权限/生产授权要求。

## 4. 变更预演和应用

1. 编辑产生新草稿，原版本、测试和审批保留。调用 change.preview 获取指纹、直接/传递影响、未知覆盖与待处理项。
2. 在同一详情区列出要改的标准、受影响成果、要补的验证、无关且保持有效的项。未知影响不能显示“0风险”。
3. 用户应用调用 change.apply，校验预演指纹及revision；过期拒绝并重新预演，不凭前端缓存执行。
4. 服务事务内失效相关baseline、阻塞依赖任务，保留旧审批历史。新版本绝不继承旧通过状态。
5. 补证据/重跑检查/重新审阅，更新派生状态。若运行失败或结果不明，保持待核实/阻断，禁止自动报交付完成。

示例：销售穿行缺件规则从「缺发票显示缺件待补」变成「缺发票必须转人工复核」。这是合成需求变更，不是审计准则建议。规则设计、接口说明、对应检查结果受影响；独立的文件格式检查保留。实际完整影响依赖项目关系，不保证示例三项等于现实三项。

## 5. UI及可访问性

UI-02聊天内新增紧凑交付卡：当前约定、未解决项、查看依据；UI-03复用详情阅读，含AC列表、版本链、变更预演与应用。Agent/Job常驻摘要继续保留，不靠新增顶层tab。普通用户看自然语言，技术ID置于详情。图示同时有文字关系，状态不只靠颜色；键盘可完成开闭及预演。

静态界面仅销售穿行示例提供完整变更交互，其余工作展示对应约定与缺口。点击应用仅更改当前页面内存，不调用模型、不修改仓库、不算授权。刷新恢复；不可伪装完成真实重测。

## 6. 接手与导出

通过原data.export导出约定正文与metadata、版本清单、可公开依据、未解决项、检查方法、风险和现有校验和。受限来源默认排除并保留「因权限排除」条目，不能静默丢弃后仍显示证据齐全。接手者可用普通文件查看；后续外部Agent回执协议未实现。
