# 产品需求规格

JP-1.0｜2026-09-25｜开发基线（代理推演，待用户审阅）

## 1. 产品定义与边界

jojo plan · 替身计划是面向 AI 工程师的 macOS 工作台。用户选择职能、配置模型、提供目标和材料，由替身按工作流程产出可审阅的成果。成功的含义是按需求完成研究、设计、实现、验证和交付，并可解释其依据。

第一版为单人本地应用，简体中文；保留制作 Skill、写文档、开发系统三个入口。支持新建容器化 Web/API 项目的全流程以及生产 pipeline 交接。不把护照校验或销售审计业务模块直接内置，它们是验证工作流的代表案例。

非目标：多人在线协作、云端常驻 Agent、任意平台的一键开发、保证真假鉴定或审计正确性、自动购买服务、技能商店、订阅计费、完整 Figma/Office 在线编辑、处理客户数据前自动推定权限。后续扩展由变更管理进入，不靠开发者自行补范围。

## 2. 用户与真实场景

| 场景 | 用户输入 | 应交付的成果 | 核心价值 |
| --- | --- | --- | --- |
| Ontology 技能组 | 模糊业务需求、研究方向、可用工具 | 多个有输入输出约定的技能及组版本，验证报告 | 把研究方法转成可靠的重复执行能力 |
| CI/CD 经验分享 | 真实经历、读者“小白”、参考资料 | 易理解、可编辑且不伪造经历的文档 | 缩短组织内容和修订时间 |
| 模型测试报告 | 模型标识、配置、测试输入与原始结果 | 可追溯的结论、局限和对比 | 减少整理证据；无结果不编造跑分 |
| 护照校验系统研发 | 图片输入与判假目标 | 从产品研究到生产的工程交付和业务评测 | 提前识别模型能力与证据范围，降低无效研发 |
| 销售穿行系统研发 | 杂乱单据、业务范围和准则 | 解析、勾稽、规则及报告系统的完整交付 | 维持材料、规则、实现和测试的一致性 |

每个项目可有多个工作项；工作项各有一个工作流运行。角色只是执行身份，项目和交付物不随角色会话消失。

## 3. 用户旅程

首次启动 → 创建项目或稍后配置 → 保存模型/工具连接并检测能力 → 选择职能 → 输入需求、材料与交付目标 → 查看将加载的技能/阶段与权限 → 开始 → 跟踪进度并处理关键决策 → 审阅版本与差异 → 验收 → 导出或批准发布。

研究过程中可以采用假设继续出草稿；未解决的关键事实不能被标为已证实。用户可切换“关键点确认”与“先推演”模式，切换只影响未来步骤，不追溯批准已有结果。

## 4. 功能需求与验收

FR 编号沿用历史稿；新增编号继续增长。实现及测试映射见研发计划。

| ID | 行为要求 | 验收标准 |
| --- | --- | --- |
| FR-01 | 模型与安装 | arm64 macOS 14+ 干净环境可打开；支持自定义服务地址、协议、型号、密钥和能力检查；失败不显示已连接 |
| FR-02 | 职能选择 | 三个入口分别加载锁定版本的流程和技能；启动前可查看、增减可选技能；缺必需能力明确提示 |
| FR-03 | 材料管理 | 支持约定格式，上传显示解析状态；每段引用可定位文件版本/页码或行号；保留失败，不静默漏件 |
| FR-04 | 研究 | 问题清单、来源、事实/推论/未知标签与研究结论一起保存；搜索不可用时标注覆盖不足 |
| FR-05 | Skill 制作 | 生成规范目录、触发说明和样例；格式检查、正反例与人工审阅记录齐全后才能启用 |
| FR-06 | 文档写作 | 支持经验分享、测试报告和通用技术文档模板；大纲、正文及修订可分别审阅；导出 MD/HTML/PDF/DOCX |
| FR-07 | 阶段管理 | 研发阶段固定依赖、必要产物和通过规则；不允许 API 绕过基线校验 |
| FR-08 | 团队宣讲 | 产品/设计交底后，架构、开发、测试分别提交理解与异议；阻断异议未关闭不得建立工程基线 |
| FR-09 | 工程设计 | 按模板交付架构、ER、数据流、模块接口、部署与非功能分析及测试设计；不适用项说明理由 |
| FR-10 | 修复循环 | 缺陷关联受测版本、复现与预期；修复只进入待复测；由新的验证结果关闭，保留失败历史 |
| FR-11 | 变更管理 | 修改已通过材料生成新版本和影响集合；相关基线失效、待执行任务阻塞；无关任务可继续 |
| FR-12 | 综合验收 | 产品、技术、市场/价值分别报告通过、需修改或证据不足；严重问题阻断交付，例外需用户接受 |
| FR-13 | 运行控制 | 暂停阻止新调用；取消停止子任务；重启保留成果、待决策和不确定执行结果；禁止盲目重放发布 |
| FR-14 | 用量限制 | 启动时配置 token 上限，显示累计、预留及未知用量；并发不能绕过预算；费用估算标明单价来源 |
| FR-15 | 追踪与交付 | 可从需求跳转设计、任务、测试与版本；ZIP 包含清单及校验和，不含密钥和默认受限材料 |
| FR-16 | 技能组 | 验证有向无环依赖、输入输出、单技能与整体样例；组版本锁定成员版本；循环依赖拒绝启用 |
| FR-17 | 文档证据 | 经验、引用、推论、实测分开；测试报告没有原始数据时显示缺口，不声称已测 |
| FR-18 | 生产交付 | 配置 pipeline、候选版本、预检、用户授权、触发、状态查询、生产验证与回滚记录；缺环境保持待配置 |
| FR-19 | 专业能力 | 可为项目选算法/数据/领域分析角色及必需能力；未验证能力作为风险与实验任务，不假定模型全能 |
| FR-20 | 规则设计 | 规则有出处/版本、条件、输入、逻辑、容差、例外、验证样本；AI 提案与接受规则分开 |
| FR-21 | 效果评测 | 样本与标签依据、模型/提示/规则版本、运行结果关联；改模型或数据后标注需重测 |
| FR-22 | 决策中心 | 决策显示推荐项、备选、影响和关联版本；先推演模式可产生假设决定，不能冒充用户批准 |
| FR-23 | 权限 | 模型材料外传、网络、文件和发布权限分别管理；运行时核验，撤销后新操作失效；Agent 不能自授权 |
| FR-24 | 版本与 Git | 自动保存草稿，封版生成不可变版本；新建代码项目隔离任务目录；检查后自动本地提交，push/merge 独立授权 |
| FR-25 | 本地数据操作 | 项目归档、备份、导出与删除应用副本；删除不波及原始导入路径；恢复保留关联完整性 |

## 5. 阶段与门槛

研发工作流：research → prd → ux → briefing → engineering（architecture/test-design 并行）→ implementation（开发/测试循环）→ final-review → release → delivered。

关键点确认模式：PRD、UX、engineering、final-review 的通过由用户作决定；briefing 的结构化覆盖与异议检查通过后自动结束；release 每次真实生产触发单独授权。阶段内角色完成后触发规则校验及独立角色检查，再提交用户，不要求用户逐条看中间消息。

先推演模式：无外部执行的研究和设计可带假设继续；其产物标为 provisional。进入代码写入之前，需用户一次接受当前有效工程基线及假设集合；未接受只能产生草案与研发计划。程序必须区分 provisional 和 approved。

技能工作流：intake → research → compose → validate → review → delivered；文档：intake → outline → draft → verify → review → delivered。技能组 review 和文档最终 review 默认由用户确认，大纲在先推演模式可自动继续。

## 6. 业务规则

- 通过结论绑定输入版本集合与产物摘要。任何影响依赖的变化令对应结论失效；草稿文字编辑尚未提交新基线时，只提示有草稿，不中断旧基线工作。
- 决定基于角色结果和确定性校验；模型的“完成”只表示提出待审阅成果，不能直接改变项目阶段。
- 任务恢复从最后持久化边界开始；副作用已发生而回执丢失时先核对，不声明 exactly-once。
- 外部规则、网页、技能文件均视为材料，不覆盖产品权限或验收标准。
- 域内未知不能被多数角色投票转换成事实；缺证据可进入待补充或显式例外。
- 所有金额存最小货币单位或十进制定点文本，不用浮点计算财务勾稽。此条用于生成的领域方案检查，不在工作台实现审计计算引擎。
- 交付证据与用户原始材料分开导出；敏感原件默认不入 ZIP、Git、模型上下文或调试日志。

## 7. 容量、性能与可用性目标

这些是验收目标，不是已测性能：默认 100 个项目、每项目 1,000 个材料/产物对象、每文件 50MB、批次最多 100 个文件/500MB；超限给出拆分指引。扫描 PDF 最多 200 页每文件，OCR 可逐批恢复。

在 D-02 基准机、10,000 条索引记录、无模型等待下：冷启动可交互 ≤5s；本地列表/详情 p95 ≤500ms；保存确认 p95 ≤1s；运行控制在 ≤1s 内进入 pending 状态。活跃任务取消默认 10s 终止宽限，外部 pipeline 不承诺被本地取消撤回。

界面支持最小 1100×720；键盘可走完整主流程；状态不只依赖颜色；文本可复制与搜索。数据损坏、磁盘满、API 限流和离线均有可恢复提示。

## 8. 首版交付定义

可安装签名/公证包、版本说明、运行依赖说明、文档、备份恢复说明以及通过测试的三类工作流。至少用合成样本跑通一个技能组、两类文档、一套新建 Web/API 系统从需求到可配置 pipeline 的完整流程。真实 production 演练只在明确授权的测试目标上验证接口；真实客户系统仍需其业务验收。

不允许把样例界面、mock Agent 或伪造测试报告作为真实能力验收通过。没有模型服务时可进行离线编辑和使用 fake runtime 测工作流，应用必须标注模拟模式。
