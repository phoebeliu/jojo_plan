# 团队交底与协作约定

JP-1.0｜本文件是准备给团队的交底包及角色视角推演。没有真实团队已听取宣讲或独立签字的事实。

## 1. 一句话任务

建设一个可安装的个人 AI 工作台，按职能加载技能，使复杂工作通过版本化产物、阶段评审和可恢复执行，从模糊需求持续推进至交付。

必读：PRD → UX → 系统/数据/接口 → 工作流 → 测试 → 任务计划。历史草稿仅查背景。

## 2. 角色与边界

| 角色 | 对结果负责 | 不应自行决定 |
| --- | --- | --- |
| 产品 | 范围、场景、业务规则、验收标准 | 模型能力未经验证就保证业务正确 |
| UI/UX | 信息架构、关键路径、状态和可访问性 | 用默认勾选把假设变成真实授权 |
| 架构师 | 组件边界、数据、协议、恢复与执行隔离 | 为完成进度而绕过权限或取消证据链 |
| 前端 | 受控交互、准确展示后端状态 | 仅依赖按钮禁用实现业务权限 |
| 后端/运行开发 | 事务、工作流、工具代理、恢复 | 让 Agent 直接写数据库批准字段 |
| 算法/数据角色 | 模型能力、样本与效果评测方法 | 合成样本结果当作真实业务通过 |
| 测试 | 需求覆盖、反例、故障、复测和证据 | 仅看 Agent 自报完成关闭缺陷 |
| 发布负责人 | 安装包、升级、发布预检与回滚 | 无授权触发客户生产变更 |
| 最终审核 | 独立检查产品、技术、价值和局限 | 用多数意见代替缺失事实 |

## 3. 必须理解的一致结论

1. 项目、工作项、任务、阶段、会话是不同对象；不能拿一个聊天线程承载全部业务状态。
2. 工作台帮助研发护照/销售系统，但首版自身不是证件核验或审计业务产品。
3. 三个工作入口共用材料、版本、权限、模型和用量服务，不做三套互不相通的小应用。
4. 暂停/取消不是简单隐藏动画；进程和外部操作必须有状态与核对机制。
5. 新版 PRD 不抹掉旧版，旧测试结果不自动升级为新版本证据。
6. 用户可授权先推演；其结果不是用户认可的正式基线。
7. 生产目标未配置时能生成发布包，但不能将项目标为已上线。

## 4. 预先识别的分歧及建议处理

| 问题 | 建议结论 | 实现影响 |
| --- | --- | --- |
| 每个角色一个持久在线进程？ | 按任务启动隔离会话，默认并发 2 | 节省成本；保留角色身份与任务历史 |
| 把所有文件发给所有角色？ | 基线摘要+精确引用+按需读取 | 降低上下文体积，证据可回查 |
| 先把 Agent 跑通再做状态管理？ | 先 fake runtime 验证工作流事务，再接真实模型 | 避免核心可靠性依赖随机模型结果 |
| 用户修改时是否停止全部任务？ | 分析依赖，只使受影响任务待复核 | 运行中的旧结果保留但不得进入新基线 |
| 是否必须额外引入 LangGraph？ | 首版明确状态机足够，暂不引入 | 领域与 RuntimeAdapter 边界保持可替换 |
| 业务效果不佳算代码 bug？ | 可回流产品、规则或模型研究 | 缺陷类型与变更类型分开 |

这些是单一代理的预检结论，真实团队在启动时可以挑战，但需提交替代方案和受影响文档，不可各自采用互斥解释。

## 5. 正式宣讲议程与交接格式

建议 60–90 分钟：产品目标/范围 15 分钟，UX 主路径 15 分钟，架构及高风险失败场景 20 分钟，测试/任务依赖 15 分钟，异议处理与责任分配余下时间。不是已举办会议。

每个角色提交：已读文档版本、本人理解、负责交付、依赖输入、前三个风险、阻断问题。交接格式统一为 input_versions、deliverable_versions、checks、open_questions、next_owner；未解决阻断问题进入决策中心。

## 6. 研发完成的最低证据

每个工作包提交关联需求、代码差异、有效测试、操作截图（适用时）、已知限制；架构/接口变化同时更新规格。检查通过后本地提交；集成分支只接受可追踪成果。文件存在或能启动不等于符合需求。
