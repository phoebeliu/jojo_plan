# 真实工作场景与产品需求映射

2026-09-25｜讨论稿。两类系统是 jojo plan 要帮助用户研发的项目案例，不是将护照或销售审计功能直接做进工作台；本轮不启动这两个系统的开发。

## 1. 已知事实

用户近期工作包括：

- 护照校验系统：客户传入一张带人脸的护照页图片，目标是鉴别是否为假。
- 销售穿行系统：传入一批杂乱文档，解析文档、形成勾稽链条、输出对应校验规则，以及是否符合审计标准的报告。
- 用户此前明确系统工作需要从零推进至生产发布。

未确定：输入样本、护照国家与版本、允许的误判率、审计准则及适用地区、具体单据类别、规则审批人、部署环境、任务量与耗时。下面的流程及验收是建议，不是已有系统的事实。

## 2. 护照校验项目如何进入 jojo plan

### 产品研究先回答什么

“假的”需要拆成可验证问题：图片是否有可见篡改、字段是否矛盾、版式是否可疑、证件是否由真实签发机关签发。单张照片能提供的证据范围不同于芯片或签发方核验。

ICAO 说明电子护照校验通过验证芯片数字签名检查数据的真实性与完整性，并可与纸面信息交叉核对。[ICAO 电子护照校验](https://www.icao.int/icao-pkd/epassport-validation)

据此作出的产品判断：只接收图片时，应先定义图像及信息一致性检测的可验证范围，不能把“未发现疑点”直接当成真实性证明。单张证件照片也没有提供判断提交者是否为持证人所需的独立比对材料；本人核验不是本次已确认需求。

### 建议流程

检查清晰度与完整性 → 识别证件类型及支持范围 → 提取字段和原图位置 → 执行已验证的规则/检测能力 → 汇总疑点、依据及局限 → 需要时进入复核或补充材料。

输出应区分：发现疑点、在当前检查范围内未发现疑点、图片不可用、证件类型不支持、证据不足。最终业务状态与处置阈值由产品阶段和领域专家确定，不预设成简单真假二选一。

### 对研发团队的要求

- 产品：定义检测范围、失败处置及误拒真证/漏过假证的业务代价。
- UI/UX：呈现可理解的结果、原图疑点位置、补传与复核路径。
- 架构与算法/领域能力：比较 OCR、专用检测服务、多模态模型等候选，并明确每种能力的证据和限制；角色按任务启用，不预定供应商。
- 测试：依据有可信标签的样本分组验证，不只测页面能否上传；分别记录识别错误、检测误判和无法判断的情况。
- 综合验收：同时检查产品目标、模型/规则效果、敏感材料处理、运行成本及上线可维护性。

## 3. 销售穿行项目如何进入 jojo plan

### 产品研究先回答什么

先明确适用的审计/内控标准、版本、业务范围、审计期间和最终报告用途。不能根据传入文档临时猜测“审计标准”。抽取准确、金额一致和符合审计标准是三个不同层面的判断。

IAASB 的相关项目说明将审计证据的获取与评价作为独立关注事项；此处仅作研究线索，不将其项目页或征求意见稿当作本项目适用的正式准则。[IAASB 审计证据与风险应对项目](https://www.iaasb.org/consultations-projects/audit-evidence-and-risk-response-isa-330-isa-500-isa-520)

### 建议流程

批量材料盘点 → 分类、解析及原文定位 → 抽取主体、单据、日期、金额等字段 → 关联业务事项 → 构建勾稽关系及未匹配项 → 根据指定标准提出规则 → 审核规则 → 执行校验 → 报告与人工复核。

示例链条（仅为假设，不代表用户实际资料）：合同 → 订单 → 发货 → 验收 → 发票 → 回款。实际项目可能有缺件、一对多、多对一、拆分付款、退货、币种或税额口径差异；不能强行凑齐或要求所有数字机械相等。

### 规则与报告应包含什么

规则至少记录来源及版本、适用条件、输入字段、计算或判断方法、容差、例外、缺失材料时的处理方式和验证样例。AI 提议的规则应标为待审核，不能自动成为权威标准。

每条结论关联具体业务事项、输入材料位置、采用规则及版本、执行结果和复核状态。结果应区分符合、发现例外、证据不足、待复核/不适用等状态；最终标签待业务定义。文件缺失不能静默补全，也不能未经规则定义直接等同违规。

### 对研发团队的要求

- 产品/领域角色：定义业务链条、标准、重要性/容差及报告责任边界。
- UI/UX：支持从报告回到规则、业务链及原始材料，处理歧义与人工纠正。
- 架构与数据能力：设计可追溯的数据解析、关联、规则执行及重跑机制。
- 测试：分别评估字段抽取、文档关联、规则执行和结论证据；覆盖重复文件、冲突资料、缺件、多币种及多对多匹配等经确认的场景。
- 综合验收：检查规则依据、报告可复核性和领域验收，不以开发单元测试通过替代业务正确性。

## 4. 对 jojo plan 的共同要求

1. 研究阶段要能识别“模型可能不具备完成目标所需能力”的风险，在承诺前给出证据与验证计划。
2. 通用团队按领域增补算法、数据或审计专业能力，且区分 AI 分析与真人专家确认。
3. 系统分析设计除架构、ER 和数据流外，应按项目补充数据字典、证据定位、规则规范、评测方案及异常流。
4. 任务同时管理代码版本、数据集版本、模型/提示配置、规则版本和评测结果；变更任何影响结果的依据都需要评估是否重测。
5. 业务效果验收和软件功能测试分别记录；假数据演示、真实评测、待验证结果明确分开。
6. 领域证据不足的任务有回流和复核机制，不能由多个 Agent 相互赞同来代替事实验证。
7. 对真实护照及业务材料，研究阶段即明确脱敏样本、发送模型的范围、保存与删除策略；具体方案在需求及架构评审中确定。

## 5. 下一轮最有用的补充

用户已确认资料与规则研究、模型效果调试、研发测试与上线都较耗时。下一步按完整项目记录各阶段的人工投入、等待与返工，识别需要反复搬运或重新解释的信息；无需用户强行选出唯一瓶颈。当前没有各阶段耗时排名，不要求此时上传真实护照或客户业务材料。
