# jojo plan · 替身计划：产品方案

版本：0.2｜状态：讨论稿｜2026-09-25

## 1. 定位

面向 AI 工程师的 macOS 工作台。用户选择职能并提供任务，由具备相应技能的替身推进工作，形成可审阅、可追溯和可复用的交付物。

目标价值：减少反复解释背景、搬运文档、组织协作、追踪问题和核对交付的时间，同时保留用户对目标、关键取舍和最终交付的控制。

已确认的是单个目标用户的工作习惯，尚未证明更广泛的市场需求。首批画像聚焦“需要同时承担产品、研究和研发协调的 AI 工程师”。

用户已提供三个真实场景：老板提出 ontology 需求，用户搜索资料后交付了 8 个 Skill，能把模糊输入转成一系列 ontology 分析输出；撰写面向小白的 CI/CD 经验分享和模型测试报告（用户称模型为“qwen3.8 27b”，具体标识未核实）；开发一个从零到发布生产的审计系统。当前未获得原始材料、耗时和具体质量问题，不推断其细节。

## 2. 三个工作入口

用户进一步明确近期系统项目为护照图片校验和销售穿行审计。工作台应支持围绕材料、领域规则、模型效果及证据追踪组织研发，详见 [真实工作场景](work-scenarios.md)。这是研发工作类型的具体化，不把两个业务系统直接并入 jojo plan，也不据此限制未来只开发审计系统。

保留用户提出的“选择职能 → 加载技能 → 开始工作”。入口名称和布局由后续 UX 阶段决定，不在本轮提前画页面。

### 制作 Skill

输入：需求、使用者、期望交付、参考材料及可用工具。

过程：澄清使用场景 → 搜索并核查资料 → 提炼可复用方法 → 编写技能包 → 正反例验证 → 用户审阅 → 保存版本。

交付：一个或一组关联的 Skill，包括 SKILL.md、必要脚本/模板/参考资料、来源记录、适用环境、验证记录。信息不足或验证失败时保持草稿，不伪装成已验证技能。后续使用发现的问题生成新版本建议，不静默修改正在执行的版本。

ontology 案例要求进一步研究“技能组”：各技能负责什么、输入输出如何衔接、模糊输入如何澄清、整体产出是否一致。8 个技能的实际名称和依赖关系尚未提供，不在产品方案中虚构。建议同时支持单技能验证和整组执行验证，并记录组版本；不能以 8 个文件生成完毕作为验收完成。

### 撰写文档

输入：文档类别、读者、目的、材料、格式与模板。

过程：材料检查 → 资料补充 → 大纲 → 撰写 → 内容与引用检查 → 审阅修订 → 导出。

交付：可编辑文档、必要来源和修订记录。已知类别包括面向小白的 CI/CD 经验分享和模型测试报告，导出格式尚未确定。内部研发文档和独立写作任务共享文档能力，但拥有各自的评审要求。

经验分享应区分亲身经历、外部资料和通用建议，控制术语并给出可跟随步骤；不能替用户编造实践经验。模型测试报告应关联准确模型标识、环境配置、测试输入、参数、原始结果、评价方法与限制。撰写报告与实际执行测试分开标记，没有测试记录时不能生成虚构跑分或声称实测完成。

### 开发系统

输入：需求、业务约束、参考材料及已有项目（是否首版支持已有项目待定）。

交付：经过综合验收的版本，以及与该版本对应的 PRD、设计、系统及测试分析、代码、测试证据、运行说明和剩余风险。用户提供的审计系统案例明确包含从零到生产发布，因此产品必须研究发布交付能力；审计对象、业务规则和部署环境尚未明确。

## 3. 开发系统的完整流程

| 阶段 | 负责与协作角色 | 主要成果 | 退出条件 |
| --- | --- | --- | --- |
| 产品研究 | 产品、研究，用户参与关键取舍 | 用户问题、资料、竞品和可行性分析、产品方案、PRD | 范围与验收清楚；关键未知有处理结论 |
| UI/UX | UI/UX、产品 | 信息架构、流程、界面及状态、交互和设计规范 | 覆盖当前 PRD；关键体验无未决冲突 |
| 宣讲与理解确认 | 产品及 UI/UX 向架构、开发、测试宣讲 | 基线材料包、角色理解摘要、问答和异议记录 | 影响后续实现的歧义已解决 |
| 系统及测试分析设计 | 架构师主导系统设计，测试主导测试分析，开发参与可实现性核对 | 架构图、ER 图、数据流、模块和接口、部署与非功能设计；测试范围、策略、场景、数据与环境方案 | 系统与测试方案覆盖 PRD/UX；依赖和冲突已处理 |
| 研发测试循环 | 开发、测试，产品/架构按问题介入 | 实现版本、测试结果、缺陷、修复、回归 | 该版本符合约定验收标准 |
| 综合验收 | 独立产品、市场、技术审核角色，用户作最终取舍 | 分维度验收报告、整改项、交付结论 | 阻断问题关闭；例外有明确接受记录 |

系统分析设计与测试分析设计可在宣讲后并行推进；测试随系统设计补充接口和非功能用例。开发开始时必须有对应范围的有效系统设计和测试依据，不能仅拿聊天摘要开工。

## 4. “宣讲”应当产生理解证据

建议交底材料绑定 PRD 和 UX 的具体版本。架构、开发、测试分别说明自己理解的目标、边界、风险和疑问；产品与 UI/UX 回答，形成决策记录。涉及需求变更的回答必须回写文档。

讨论应围绕具体问题结束：解决、延后并说明影响、或需要用户裁决。仅有角色发言或一致说“收到”不算宣讲完成。讨论回合和成本需受限，无进展时暴露分歧。

## 5. 变更与返工

示例（虚构，仅用于说明）：PRD v1 规定“成员可以导出数据”，开发中改成“仅管理员可以导出”。

系统应建立变更单，关联相关 PRD 条目，识别界面入口、权限设计、接口实现和测试用例；产品与架构形成新结论，更新受影响材料；相关任务进入待调整状态，未受影响任务可继续。新版本重新通过必要评审后再执行回归。旧版的测试通过记录保留，但不能证明新版通过。

| 问题类型 | 回流对象 | 关闭依据 |
| --- | --- | --- |
| 实现缺陷 | 开发 → 测试 | 修复版本与复测/回归证据 |
| 需求含糊或冲突 | 产品，必要时用户 | 更新后的需求与决策记录 |
| 架构不可行或跨模块问题 | 架构、开发、测试 | 修订方案及影响分析 |
| 交互问题 | UI/UX、产品 | 更新设计及体验验证 |
| 验收发现价值或市场问题 | 产品、市场审核、用户 | 补充证据、调整范围或明确接受限制 |

重复失败不能无限消耗模型。建议支持预算、轮次和无进展检测，触发后保留成果并请求处理，而不是自动降低验收标准。

## 6. 替身、技能和团队的关系

替身由职能、任务、可加载技能、工具能力、模型配置和工作边界共同构成。一个角色可以按任务临时启用，不需要所有角色常驻。

技能提供可复用方法；工作流决定阶段顺序和交接条件；交付物承载工作依据；模型负责推理与生成；工具完成搜索、文件处理、开发和测试。共享的是受控项目事实，不是把所有历史对话复制给每个角色。

审核角色应有独立会话和检查过程，可按需配置不同模型，但换模型不等于独立性得到保证。应靠验收标准、实际测试和证据避免自我背书。

## 7. 用户控制与成果管理

建议用户能随时知道：当前阶段、有效基线、执行者、已完成成果、待决策问题、失败原因和已消耗资源。

工作应支持暂停、恢复、取消、修改材料、提出变更及导出成果。修改已批准文档生成新版本，不能覆盖旧验收依据。哪些阶段由用户批准、哪些允许按规则自动通过，需进一步确认。

审计系统案例的交付目标包含生产发布。建议综合验收通过后形成发布候选版本，检查目标环境、配置、数据迁移、监测与回滚方案，完成发布授权后执行，随后验证生产关键路径和健康状态，再确认交付完成。发布失败进入恢复或回滚流程，不能把上传成功当作上线验收通过。生产操作的授权规则尚待用户确定。

## 8. 范围原则

完整产品保留三类工作，不预设先缩减为 Skill 工具。首版应在调研后确定支持的任务类型及复杂度，开发系统即使只支持一种系统类别，也应保留完整流程和真实返工机制。

候选延后项：技能市场、云端团队账户、计费、多设备同步、大量第三方连接器。以上只是控制范围的建议，尚未获用户确认。

优先验证结果：能否减少人工组织工作、能否使文档与交付版本一致、能否把问题送回正确角色。角色数量、生成字数和讨论条数不作为主要成功指标。
