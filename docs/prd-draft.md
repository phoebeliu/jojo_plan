# jojo plan PRD 讨论稿

> 历史讨论材料：当前开发基线见 [JP-1.0 阅读入口](spec/00-reading-guide.md)，当前待拍板清单见 [用户决定](spec/01-owner-decisions.md)。本文保留原阶段结论。
版本：0.2｜2026-09-25｜状态：需求整理，非开发基线

本稿把已知意图转成可讨论需求；不表示产品调研已结束。UI/UX、系统分析设计及研发应等待产品阶段评审。除明确来自用户的要求外，以下具体行为是建议方案。

## 1. 目标与用户

目标用户：使用 Mac、需要制作可复用技能、撰写文档及协调完整系统交付的 AI 工程师。

目标：使用户能按职能启动工作，通过替身与技能形成可核查交付；完整研发过程中维持需求、设计、实现和验证的一致性。

成功指标候选：每任务人工协调时间、交付一次验收通过率、变更遗漏率、任务恢复成功率、技能再次复用的通过率。须先采集真实任务基线再定数值目标，不预填提升百分比。

用户确认研究、模型调试、研发测试与上线均耗时，故评估应覆盖整个交付周期。建议分别记录人工投入、Agent 执行、等待决策与返工原因；并行任务耗时不直接相加作为项目历时，自动记录不能冒充准确的人工工时。以交付质量不下降为前提评估节省，不以生成速度或角色发言数代替成效。

真实场景已由用户补充：ontology 研究后交付 8 个关联 Skill；小白 CI/CD 经验分享；“qwen3.8 27b”模型测试报告（名称按用户原话，未核实）；审计系统从零开发到生产发布。这些是用户案例，不是本产品已完成的能力。

## 2. 需求与验收示例

系统工作已具体化为护照图片校验和销售穿行审计，详见 [案例分析](work-scenarios.md)。以下新增项是从案例提炼的工作台能力建议，领域系统的详细 PRD 仍需各自形成。

| 编号 | 功能需求 | 可观察的验收结果 |
| --- | --- | --- |
| FR-01 | 安装与模型配置 | 用户能在目标 macOS 安装启动，保存模型配置并完成连接/能力检查；失败时给出可处理原因 |
| FR-02 | 按职能启动任务 | 选择制作 Skill、写文档或开发系统后，加载对应工作流程与适用技能，能查看和调整本任务配置 |
| FR-03 | 项目材料管理 | 附加的材料可检索和引用；明确区分用户事实、外部资料、推论及未确认假设 |
| FR-04 | 研究与来源 | 研究结论关联可访问来源及查阅时间；不可核实的信息标记为未确认，搜索失败不生成虚假引用 |
| FR-05 | 技能制作与验证 | 导出完整技能包及验证记录；验证失败时不能显示为已验证版本；任务固定使用选定版本 |
| FR-06 | 文档写作与交付 | 文档按约定模板和格式生成、审阅、修订和导出；具体格式依真实工作样本确定 |
| FR-07 | 开发阶段管理 | 研究/PRD、UX、宣讲、系统及测试分析、研发测试、综合验收阶段有明确材料、状态及通过条件 |
| FR-08 | 宣讲与异议 | 各参与职能形成理解与疑问，关键异议有处理结论；回答改变需求时回写新版本 |
| FR-09 | 系统与测试分析产物 | 记录架构、ER、数据流、模块接口等系统分析以及测试策略与场景；不适用产物说明原因，不能空文件算完成 |
| FR-10 | 开发与测试循环 | 测试问题关联需求、受测版本、复现步骤、预期与实际；开发提交修复后由测试复验关闭 |
| FR-11 | 需求及设计变更 | 修改已建立的基线后产生变更及影响清单；受影响任务和验证记录待复核；旧历史仍可查询 |
| FR-12 | 综合验收 | 产品、市场、技术审核分别出结论与证据；不通过项进入整改；最终状态与具体交付版本绑定 |
| FR-13 | 暂停恢复与取消 | 退出再打开能恢复已保存成果和等待项；取消后不再启动新工作，已运行操作的结果明确可查 |
| FR-14 | 成本与循环控制 | 显示可获得的模型/工具用量；估算费用与实际费用区分；预算或无进展限制触发后可恢复处理 |
| FR-15 | 成果追踪与导出 | 从需求可找到相关设计、任务、测试、缺陷和交付版本；导出成果时附版本清单与运行说明 |
| FR-16 | 关联技能组 | 支持把模糊需求拆分为多个技能，声明职责及输入输出关系；记录组版本，验证单项与整体执行结果 |
| FR-17 | 文档证据类型 | 经验分享区分真实经历与补充资料；模型报告区分原始测试结果、推论及待测试项，能定位环境、参数和评价方法 |
| FR-18 | 生产发布交付 | 对需上线的项目管理发布候选、环境准备、迁移、回滚、发布授权、执行及生产验证记录；失败时不显示交付完成 |
| FR-19 | 领域能力与可行性研究 | 团队能按项目调入领域、算法及数据能力；关键模型或数据能力未经验证时明确列为待验证，不仅评估代码实现 |
| FR-20 | 规则与证据设计交付 | 对规则判断类项目，形成规则来源、适用范围、版本、输入输出及证据追溯要求；待审核规则与已接受规则分开 |
| FR-21 | 业务效果评测管理 | 关联数据样本、标签依据、模型/提示/规则版本、指标及实测结果；业务效果与软件测试分别验收，关键变更触发评测复核 |

## 3. 关键业务规则

BR-01：阶段通过绑定具体输入及交付物版本，不以角色消息代替通过记录。

BR-02：阶段建议状态为未开始、执行中、待审阅、需修改、已通过；运行失败、等待输入、暂停是独立运行状态，避免把技术失败当成业务驳回。

BR-03：审核结论建议为通过、需修改、证据不足；若允许带例外交付，必须由有权用户明确接受例外。自动重试不能自动更改目标。

BR-04：新版本使受影响的下游结论待复核，不删除历史结论，也不把全部工作一律清空。

BR-05：讨论只调入与问题相关的角色；保留问题、备选方案、结论与负责人。达到讨论限制时呈现未决分歧。

BR-06：技能和网页资料属于工作材料，不能自行扩大工具权限或改变项目审批规则。

BR-07：市场审核应区分“分析推论”和“真实用户/市场证据”；缺少后者时不得宣称已证实需求或商业可行性。

## 4. 完整验收场景（待后续测试分析细化）

AC-01：给出一个明确 Skill 任务，完成资料核查、包生成、示例验证和导出；再次调用时可识别其版本及适用范围。

AC-02：为给定读者撰写文档，发现材料矛盾时提出待决策项；修订后导出，能够定位引用依据。

AC-03：开发任务在 PRD 待审阅时退出应用；重启后仍停留于同一版本的审阅，不自动进入设计。

AC-04：宣讲中测试发现 PRD 与 UX 矛盾；问题得到澄清和文档更新前，不建立相互冲突的研发依据。

AC-05：测试发现可复现缺陷；修复后运行相关回归，缺陷关闭记录绑定修复版本。开发声称修复但未复测时保持待验证。

AC-06：开发中需求改变；系统追踪受影响的设计、任务和用例，新的交付不能使用旧需求的通过结果冒充验收。

AC-07：综合验收发现产品目标未满足；返回产品讨论并形成调整，完成必要的设计、研发及测试回路后重新验收。

AC-08：模型限流、无权限或修复持续无进展时，任务进入可解释的等待/失败状态，保留已完成成果，不无限重试。

AC-09：给出 ontology 类模糊需求，生成有关联的技能组，展示技能职责和结果衔接，使用代表性输入核验整组输出；需求信息不足时保留假设或请求澄清。具体 8 个技能的内容待用户提供后建立实际样本。

AC-10：用真实 CI/CD 经历形成小白可读分享；用真实模型测试数据形成报告。缺少原始结果时明确显示证据不足，不把网上跑分冒充用户实测。

AC-11：审计系统完成综合验收后，按已授权发布方案上线并验证生产关键路径；发布或数据迁移失败时执行约定的恢复方案，保留记录。业务审计范围和生产环境待补充后形成具体用例。

AC-12：护照校验项目只有图片输入时，团队明确可验证范围、误判评测和证据不足处置；不能仅凭演示可运行就通过业务验收。

AC-13：销售穿行项目产生规则与报告时，团队定义材料定位、勾稽关系、标准版本及结论的追踪要求；缺件、冲突和多对多关系进入测试范围，具体准则待用户确定。

AC-14：更换模型、规则或数据集后，相关评测结论待复核，保留原有版本结果；不让旧版业务评测自动证明新版本有效。

## 5. 非功能需求候选

- 数据可靠性：已保存版本可恢复；并发修订检测冲突；恢复时核查不确定的外部执行结果。
- 本地数据与权限：项目可保存在本地；凭据使用系统安全存储等合适方案，不进入项目导出或运行日志。具体实现由架构阶段确定。
- 可观测性：每次工作记录角色、输入版本、模型配置、工具操作及成果；失败原因足够定位。
- 桌面体验：生成任务不阻塞主要交互；暂停与取消及时反映状态。响应时间、资源占用的数值待目标机型明确后确定。
- 可移植性：文档和技能可导出；不依赖只有原会话才可理解的上下文。
- 运行生命周期：睡眠、退出、断网和更新后的任务行为必须明确；本机休眠期间不承诺持续执行。

## 6. 当前不能定稿的事项

真实任务和两类文档已明确，审计系统交付需要生产发布。尚需补充原始样本、主要耗时环节、审计业务范围与部署环境、首版支持边界、人工评审节点、使用模型服务、可接受成本、是否远程持续执行、分发范围与目标机型。详见 [待决策与验证计划](decisions.md)。

本阶段交给 UI/UX 的材料应是经评审的 PRD、用户场景、业务规则及异常情况。系统架构图、ER 图与数据流图由后续架构师依据 PRD 和 UI/UX 形成，本稿不抢先确定实现设计。
