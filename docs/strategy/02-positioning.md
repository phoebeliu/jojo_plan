# 产品定位与功能取舍 S1

## 用户、任务与购买触发

第一批服务**亲自对结果负责的 AI 工程师/小型交付负责人**：从老板或客户一句含糊要求开始，要交研究、文档、系统，并且经常回改。阅读说明不要求会技术；首版操作用户仍需能配置模型和开发环境，不定位「所有普通人一键开发生产系统」。

购买触发假设：第二次需求变化时，负责人不知道哪些文档、规则、代码和测试仍有效，需要花很多时间重新解释和核对。用户已证实这些项目费时间，但没有确认时间主要花在交接；必须观察真实工作，不能把我们的推断冒充访谈结论。

**一句话定位：jojo plan 帮你把模糊任务变成可验收的交付，并在每次修改后找回需要重做、重测和重新确认的部分。**

首次价值时刻：把销售穿行系统的「缺发票是否算通过」从聊天要求变成 AC-02；用户改变规则后，看见规则设计、接口说明、样例验证需要复核，旧的通过记录不再支持新版本；接手者可沿同一条要求查看依据。这比展示五个角色头像更能解释为什么用它。

## 同一闭环，三种交付规模

| 工作 | 先约定什么 | 依据与检查 | 可带走什么 |
| --- | --- | --- | --- |
| Ontology Skill 组 | 支持的输入、输出、未知处理、组依赖 | 正反例与整体样例；失败输入成为回归候选 | 有适用边界和版本的 Skill 包 |
| 经验分享 / 模型报告 | 读者、文章用途、事实/实测声明 | 引用、原始记录、渲染检查；缺实测保持缺口 | 正文、依据、版本与局限 |
| 系统研发 | 功能、边界、数据与生产验收 | PRD→UX→架构→实现→测试→综合审核 | 源码、文档、检查记录和部署交接 |
| PPT（后续） | 受众、决策目标、页数、可编辑性 | 数字溯源、叙事审阅、渲染溢出和字体检查 | PPTX、预览和依据；未接生成器则不可运行 |

审计项目下有销售穿行、IPO 工作；护照校验项目与审计项目同级。以上是「研发这些系统」，jojo 不直接替代审计人员作专业结论，也不从单张图片承诺鉴定护照真实性。

## 优先级变化

| 层次 | 保留/调整 | 对原方案的具体影响 |
| --- | --- | --- |
| P0 价值闭环 | 交付约定、证据定位、变更预演、重验状态、可导出交接包 | 优先贯通 FR-11/12/15/17/20/21，先用一条销售穿行规则跑通 |
| P0 执行基础 | 模型/权限/预算/恢复、主对话、Agent 与 Job 可观测 | 仍必要；不能为了商业演示绕过安全和执行可靠性 |
| 首版三类工作 | Skill、文档、系统 | 不取消已确认范围，但按薄切片逐个实现，共用记录系统 |
| 减少仪式 | 简单文档只保留必要约定/证据/审阅 | 系统仍按用户五阶段流程；不新增14个管理页面 |
| 后置 | PPT生成器、更多运行引擎、市场、云托管、多人账户 | PPT继续显示能力缺口；不扩张为同时运营四套Agent底座 |
| 取消宣传 | 全能、无人验收、永不出错、自动进化胜过Hermes、独家多Agent | 不能以愿景代替功能可用性 |

## 接入现有工具与可退出性

已确认 Pi adapter 继续作为首个运行实现；不因为竞品研究临时换底座。首版导出中包含目标、材料权限范围、锁定版本、检查方法、开放问题和成果清单，人可以交给现有工具继续做。**可携带文件不等于已实现 Codex/Claude/Hermes/DSH 原生双向同步。** 自动导入执行回执、跨引擎派单后置，另出协议和兼容性实测。

Agent返回「已完成」只形成待验证成果，不形成可信测试记录。外部工具的日志默认当导入材料，必须检查来源与目标版本后才可参与验收。客户能够完整导出、自行继续；留存来自复用节省时间，不能靠扣留成果。

## 从旧定位迁移

当前统一聊天/执行面板继续存在；在聊天中增加简短「交付约定」卡，点开同一个详情区看标准、依据与变更。没有新的顶层 tab。主界面回答：现在要交什么、卡在哪、我需要决定什么。执行面板回答：谁在做、哪些后台任务、有没有失败。二者不能互相替代。

实现详细约束与既有FR映射见[交付闭环规格](../spec/16-delivery-contract.md)。真实专业规则、上线阈值与样本由项目所有者决定；演示数字不能成为默认业务规则。
